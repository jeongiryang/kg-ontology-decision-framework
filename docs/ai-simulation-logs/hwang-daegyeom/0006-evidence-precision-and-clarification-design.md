## 1. 작업 목적

로그 0005 직후 담당자가 화면을 직접 확인하면서 결함과 물음이 이어졌다. 그 논의에서
**정확성을 커버리지보다 우선한다**는 기준이 확정됐고, 그 기준에서 앞선 판단 두 가지를
뒤집었다. 이 로그는 그 판단 변경의 이유와 근거를 남긴다.

## 2. 요청 내용 요약

담당자 요청을 시간순으로 적는다. 뒤로 갈수록 앞의 답을 되짚어 기준을 좁히는 흐름이다.

1. 화면에서 `자료구조` 근거를 보니 `고급자료구조` 행에도 빨간 박스가 있다. 옳은 동작인가.
2. 잘못된 근거를 다는 현상을 어떻게 없앨 수 있나.
3. 근거가 있으면 무조건 근거를 달고, 그 근거 강조도 무조건 관련 근거여야 한다.
4. 강조 99.8%의 나머지는 무엇이 문제인가. 100%로 만들 수 없나.
5. "검토가 안 끝난 사실"이 무슨 말인가.
6. 전체 프로세스를 설명해 달라. 답변을 하드코딩으로 만든 것은 아닌가.
7. 답변 틀을 Python이 미리 만들면 답변이 매우 제한적이지 않은가.
8. 근거 없는 문장을 못 하게 하려면 Python 제한과 LLM 생성 중 무엇이 확실한가.
9. LLM으로 답변을 만들어내는 것은 하지 말자.
10. LLM이 현재 관여하는 곳은 어디고, 그것이 할루시네이션을 없앨 수 있나.
11. 엉뚱한 것에 답하는 것을 줄이려면 어떻게 하나. LLM 없이도 답변이 가능한가.
12. 정확성이 더 중요하다. LLM을 쓰되 엉뚱한 답이 없는 방법은 없나.
13. 부족한 정보를 되물어서 사용자가 채우면 답할 수 있게 하면 되지 않나.
14. 자유 입력 말고 선택지를 주는 방식으로 설계하자.
15. 웹 화면도 직접 확인할 수 있게 함께 고쳐라.
16. 넓히기로 여러 요건을 한꺼번에 답하지 말고 이 경우에도 선택지로 되물어라.
17. 되묻기를 한 번만 하지 말고 필요하면 이어서 타고 들어가게 하자(방향만 제시).

## 4. 수행한 작업

### 4.1 잘못된 근거 강조 수정과 재설계

담당자가 화면에서 확인한 사례부터 시작했다. `자료구조`(CDA0008) 근거인데 같은 표의
`고급자료구조`(CDA0143) 행의 `Data Structure` 에도 강조가 들어갔다.

원인은 한 Evidence 가 표의 **한 행**인데, 조각 중 일부가 다른 행에도 그대로 나오기
때문이었다. 로그 0004 에서 강조 성공률을 76%→91%로 올리려고 검색어를 잘게 쪼갠 것의
부작용이다.

강조를 3단계로 재설계했다.

| 단계 | 방법 | 효과 |
|---|---|---|
| 1 | 조각을 글자 그대로 검색하되, 한 번만 나온 조각으로 행을 먼저 고정하고 여러 곳에 나온 조각은 그 행 안의 것만 채택 | 오탐 제거 |
| 2 | 행 단위 글자쌍(2-gram) 유사도 대조 | 정규화된 문장·깨진 텍스트 레이어 대응 |
| 3 | 근거의 `table_name`·`section_title` 로 절 위치 | 큐레이터 주석형 근거 대응 |
| — | 셋 다 실패하면 표시하지 않음 | 없는 위치를 만들지 않음 |

2단계가 결정적이었다. 발췌 PDF 의 텍스트 레이어가 다음처럼 깨져 있어 글자 그대로는
찾을 수 없는 근거가 많았다.

```text
근거 원문: 학과별 교양과목 이수학점은 34학점 이상 42학점(예술대학 50학점) 이내에서…
PDF 실제 : 가학과별 교양과목 이수학점 . 은  학점 이상  학점예술대학  학점이내에서…34 42 ( 50 )
```

### 4.2 통제어휘를 속성별로 찾도록 수정 (결함)

되묻기 선택지 문구를 온톨로지에서 유도하는 설계를 검토하다가 기존 결함을 발견했다.
`vocabulary_labels()` 가 통제어휘 값을 **전역 키**로 매핑하고 있었다. `MAJOR` 는
`competency_type` 에서는 "전공능력"이고 `major_type` 에서는 "전공"인데, 먼저 읽힌 쪽이
이겨 검색 색인에 잘못된 표기가 실렸다.

명세의 `controlled_vocabulary` 선언을 읽어 `(속성, 값) → 표기` 로 키를 바꿨다.

### 4.3 실험한 뒤 되돌린 것

담당자 질문 11번("LLM 없이 가능한가")에 답하려고 검색 단독 성능을 재면서 두 가지 개선을
시도했고, **둘 다 되돌렸다.**

| 시도 | 검색 단독 1순위 | 실제 경로 | 판단 |
|---|---|---|---|
| 기준 | 9/19 | 19/19 | — |
| 근거의 `section_title` 도 색인 | 7/19 | 19/19 | 되돌림 |
| 학과명을 주제어에서 제외 | 11/19 | 19/19 | 되돌림 |

되돌린 이유는 두 가지다.

- **실제 경로(LLM+검색)에 이득이 실측되지 않았다.** 어느 조합이든 19/19 였다.
- 관련 질문과 무관한 질문의 점수 간격이 2.97배에서 1.93배로 좁아져, 안전 여유를 재는
  테스트가 깨졌다.

측정되지 않은 이득을 위해 안전 여유를 깎지 않는다는 기준을 스스로에게도 적용했다.

### 4.4 LLM 없이 답변이 가능한지 실측

같은 19문항으로 검색만 써서 모드를 골랐다.

| 방식 | 1순위 정답 | 3순위 안 |
|---|---:|---:|
| 검색만 | 9/19 (47%) | 16/19 (84%) |
| LLM + 검색 | 19/19 (100%) | — |

**아직 LLM 없이는 안 된다.** 벽은 어휘 불일치다.

```text
질문   : "졸업 후 진출 분야는?"
데이터 : "기업체/연구소/금융기관의 프로그램 개발실"
          겹치는 낱말 0개
```

글자 대조로는 원리적으로 못 넘고, LLM 은 넘는다(실제로 이 문항에서 `CAREER_FIELD_LIST`
를 정확히 골랐다). 지금 LLM 이 하는 일이 바로 이 다리 놓기다.

### 4.5 되묻기 흐름 설계와 구현

담당자 제안(13·14번)을 받아 설계를 확정했다. 원칙은 하나다.

> **서버가 데이터에서 만든 선택지만 계획에 들어간다. 사용자 자유 입력은 계획에 직접
> 들어가지 않는다.**

선택지 생성 규칙은 다음과 같다. 다섯 종 전부 적재 데이터·명세에서 나오며 코드에 값을
적지 않는다.

| 부족한 것 | 선택지 출처 |
|---|---|
| `DEPARTMENT` | `Department.name_ko` |
| `ACADEMIC_YEAR` | `CurriculumVersion.academic_year` |
| `COURSE_IDENTITY` | 검색 상위 `CourseOffering` 의 과목명·학수번호 |
| `RULE_TOPIC` | 검색 상위 `Rule` 의 `description_ko` |
| `QUESTION_INTENT` | 검색 상위 후보의 사실 종류 → 명세 `name_ko` + 통제어휘 `description_ko` |

마지막 줄은 모드 14종 중 13종에 고유한 문구를 준다(집계 2종만 겹치며, 이는
`aggregate_type` 별로 나누면 해소된다).

이어가기는 **서버 무상태**로 한다. 브라우저가 원래 질문과 확정값을 들고 매 요청에 함께
보낸다. 대화 기록을 쌓는 것이 아니라 같은 질문의 빈칸을 채우는 구조다.

```text
1턴  {"question": "전공필수 과목은?"}
     → CLARIFICATION_REQUIRED + options

2턴  {"question": "전공필수 과목은?", "resolved": {"department_id": "…"}}
     → ANSWERABLE
```

`resolved` 는 두 겹으로 잠근다. 서버가 선택지를 **다시 생성해** 그 안의 값인지 대조하고,
통과한 값은 계획 정규화 마지막에 덮어써 계획 모델이 바꾸지 못하게 한다.

설계대로 구현을 마쳤다. 화면에서 실제로 확인한 왕복은 다음과 같다.

```text
1턴  "캡스톤 과목 알려줘"
     → CLARIFICATION_REQUIRED  "어떤 과목을 말씀하시나요?"
        · 산학캡스톤디자인1(CDA0167)   · 산학캡스톤디자인2(CDA0168)

2턴  {"resolved": {"course_code": "CDA0167"}}
     → ANSWERABLE  근거 1건
        "산학캡스톤디자인1는 3학년 1·2학기에 개설됩니다. …"

조작 {"resolved": {"course_code": "ZZZ9999"}}
     → 값이 무시되고 같은 선택지로 다시 되묻는다
```

구현 중 기존 결함 다섯 가지가 드러나 함께 고쳤다. 되묻기를 붙이자 종전에는 드러나지
않던 경로가 열리면서 한 번에 보인 것들이다.

| 증상 | 원인 | 조치 |
|---|---|---|
| 사용자가 고른 값으로도 계획이 서지 않음 | 되묻기 응답에서 모델이 `evidence_required` 를 비워 두는데 계약은 참만 통과시킴 | 근거 요구는 모델이 정할 값이 아니므로 계획 조립에서 항상 참으로 둔다 |
| `자료구조은 3학점입니다` | 과목 렌더러가 조사를 글자와 무관하게 고정 | 오늘 만든 조사 계산을 과목 렌더러에도 적용 |
| `자료구조는 뭐지?` 에 학점만 답함 | 계획 모델이 고른 한 속성만 요청 | 한 과목을 물으면 개설 정보를 온전히 요청하도록 구조적으로 보강 |
| 과목을 고른 뒤 Claim 이 비어 답변 실패 | 답변 주어를 만들 `name_ko` 가 요청 필드에 없음 | 과목 답변 필수 필드에 과목명을 포함 |
| 고른 과목으로 조회했는데 0건 | 계획 모드가 권장과목 조회로 남아 그 family 의 `course_code` 로 조회됨 | 선택지가 뜻하는 모드를 함께 선언하고, 고른 값이 모드를 정하도록 함 |

그리고 오답 방지 가드의 적용 범위가 좁았던 것을 넓혔다. 질문이 적재된 과목을 이름으로
지목했는데 계획이 그 과목을 가리키지 않으면 답하지 않는 검사가, 되묻기를 READY 로 바꿀
때만 걸려 있었다. 계획 모델이 곧바로 READY 를 내면 걸러지지 않아 `자료구조는 몇 학기?`
질문에 권장 교양 과목 목록이 근거와 함께 나오는 것을 화면에서 확인했다. 정상 경로에도
같은 검사를 걸었다.

### 4.6 넓히기 경로 제거 (담당자 화면 확인에서 나온 방향 전환)

담당자가 화면에서 두 가지를 지적했다.

```text
"얼마니러ㅏ님"        → 이수요건 전체를 쏟아냄
"균형교양 이수요건은?" → "확정하지 못해…" 하며 요건 두 개를 한꺼번에 보여 줌
```

둘 다 로그 0004에서 만든 **넓히기**(좁히지 못하면 관련 요건을 모아 답한다) 경로다. 그때는
되묻기가 없어 "거절보다는 낫다"가 근거였다. 지금은 같은 후보를 **고를 수 있게** 줄 수
있으므로 넓히기가 차선이 아니다. 경로를 제거하고 되묻기로 대체했다.

되묻는 **종류**는 고정 순서로 정할 수 없었다. 학과는 적재돼 있으면 언제나 후보가 생겨
먼저 걸리고, 과목 후보는 이수요건 질문에도 약하게 걸려 더 맞는 선택지를 가렸다. 그래서
검색이 무엇을 짚었는지 보고 되물을 종류를 정하도록 했다.

| 질문 | 검색이 짚은 것 | 되묻는 종류 |
|---|---|---|
| 균형교양 이수요건은? | Rule | 이수요건 선택지 |
| 캡스톤 과목 알려줘 | CourseOffering | 과목 선택지 |
| 얼마니러ㅏ님 | 없음 | "무엇을 알고 싶은지" 메뉴 |

이 과정에서 **사용자 선택이 계획에 반영되지 않는 경로** 네 가지가 드러나 함께 고쳤다.

| 증상 | 원인 | 조치 |
|---|---|---|
| 고른 값이 무시됨 | 사용자 선택을 계약 검사 **뒤에** 반영 | 검사보다 먼저 반영한다 |
| 고른 과목으로 조회했는데 0건 | 모드가 권장과목 조회로 남아 그 family 의 `course_code` 로 조회 | 선택지가 뜻하는 모드를 함께 선언하고 고른 값이 모드를 정한다 |
| 모드를 바꾸니 Cypher 생성 실패 | 이전 모드의 요청 필드가 그대로 남음 | 새 모드가 줄 수 있는 필드만 남기고 필요한 필드를 보강 |
| 3회 시도를 다 쓰면 안전 실패 | 넓히기가 메우던 자리 | 되묻기로 끝나도록 바꿨다 |

## 6. 주요 결정과 이유

이 로그의 핵심은 아래 세 가지 **판단 변경**이다. 앞선 답을 뒤집은 것이므로 이유를 함께
남긴다.

### 6.1 "LLM 생성 + 검증" 추천 → **철회**

처음에는 답변 표현을 넓히려고 하이브리드(LLM 이 문장을 쓰고 검증기가 값을 대조)를
추천했다. 담당자가 "확실히 가능성이 없어야 한다"는 기준을 제시하면서 철회했다.

값 대조는 숫자·고유명사는 잡지만 **뜻의 왜곡은 못 잡는다.**

```text
승인된 행 : 자료구조 / 이수구분 = 전공선택 / 부전공필수 표시 있음
LLM 출력  : "자료구조는 부전공 필수가 아닙니다."   ← 값은 전부 승인된 행에 있음
```

부정어·조건어를 검사하려면 검증기가 자연어를 이해해야 하고, 그러면 검증기를 무엇으로
검증하느냐는 같은 문제로 되돌아간다. **확률을 낮추는 것과 경로를 없애는 것은 다르다.**

Python 조립은 답변이 승인된 행의 함수이므로 나올 수 있는 문장이 유한하고, 행에 없는 값이
들어갈 경로가 존재하지 않는다. 담당자가 9번에서 이 방향을 확정했다.

### 6.2 "정확성 100% + 커버리지 유지는 불가능" → **정정**

12번 질문에 "논리적으로 불가능"이라고 답했으나 이는 **한 번에 답해야 한다는 전제**에서만
맞다. 담당자가 13번에서 되묻기를 제안하면서 전제가 깨졌다.

| | 한 번에 답할 때 | 되묻기가 이어질 때 |
|---|---|---|
| 확신 없을 때 | 답하거나(위험) 거절하거나(손실) | 물어본다 |
| 정확성 100% | 커버리지 희생 | 커버리지 유지 |

거절이 막다른 길이 아니라 한 단계가 되면, 확신 없이 답하지 않으면서도 커버리지를 잃지
않는다. 전제를 좁게 잡은 것이 오류였다.

### 6.3 되묻기를 자유 입력이 아니라 선택지로

자유 입력으로 다시 받으면 사용자의 답("컴공요")을 다시 해석해야 하고, 그러면 LLM 추측이
되돌아온다. 선택지를 데이터에서 만들면 세 가지가 함께 해결된다.

- 사용자가 **없는 값을 고를 수 없다**(선택지가 적재된 값뿐이다)
- LLM 재호출이 필요 없다 → 오해할 자리가 없다
- 사용자가 고른 값은 가장 신뢰도 높은 정당화 출처가 된다

담당자가 14번에서 이 방향을 지정했다.

### 6.4 "넓혀서 답한다" → **제거**

로그 0004에서 만든 넓히기는 되묻기가 없던 시절의 차선책이었다. 근거는 "거절보다는 낫다"
였다. 되묻기가 생긴 지금은 같은 후보를 고를 수 있게 주는 편이 낫고, 넓히기는 묻지 않은
요건을 답에 섞는 부작용만 남는다. 담당자가 화면에서 두 사례를 확인하고 지적해 제거했다.

이 판단은 로그 0004의 4.3("정밀도 실패를 답변 거부로 처리하던 지점을 넓히기로 바꿨다")을
뒤집는다. 그때의 전제(되묻기가 이어지지 않는다)가 더 이상 참이 아니기 때문이다.

### 6.5 그 밖의 결정

- **되묻기 문구는 Python 이 코드에서 조립한다.** LLM 이 쓰게 하면 답변 문장과 같은 위험이
  생긴다. 담당자 확인을 받았다.
- **`QUESTION_INTENT` 선택지는 LLM 이 혼자 고르던 자리를 사용자에게 넘긴다.** 클릭이 한
  번 늘지만 오분류가 사라진다. 담당자 확인을 받았다.
- **강조는 못 찾으면 표시하지 않는다.** 덜 보여 주는 것은 근거를 덜 보여 줄 뿐이지만,
  잘못 칠하는 것은 없는 근거를 만들어 낸다.
- **서버 세션을 쓰지 않는다.** 저장소·만료·정리·동시성이 따라오고 재시작에 대화가 사라진다.
  이 규모에 맞지 않는다.

- **되묻기 상한 `MAX_ROUNDS = 3` 은 아직 실측으로 정한 값이 아니다.** 연쇄 되묻기를

- **브라우저가 예전 화면 문서를 캐시하면 답변이 화면에 나오지 않았다.** `index.html` 을

- **평가셋 50문항은 아직 한 번도 돌리지 않았다.** 지금까지의 모든 수치는 에이전트가 만든

## 10. 다음 작업 제안

### 10.1 순서가 중요하다

되묻기를 먼저 만들고 **그 다음에** "정당화 안 되면 거절"을 켜야 한다. 순서가 반대면
거절만 늘고 사용자는 막힌다.

```text
1. 되묻기 이어가기 구현      ← 안전망 먼저
2. 정당화 필수화(엄격 모드)  ← 그 위에 얹기
3. 50문항으로 측정
```

### 10.2 정당화 출처를 계약으로 만든다

지금 계획 보정은 "정당화되면 채택"이고 "안 되어도 진행"이다. 이를 "정당화되지 않으면
되묻기"로 뒤집으면 엉뚱한 답이 구조적으로 막힌다. 정당화 출처는 다섯 가지이며 전부
기계가 확인할 수 있다.

1. 질문에 그대로 있는 값
2. 온톨로지가 선언한 통제어휘 한국어 표기
3. 데이터가 유일하게 정하는 범위
4. family 선언의 기본값
5. **사용자가 선택지에서 고른 값** (되묻기가 추가하는 출처)

5번이 생기기 전에 1~4번만으로 필수화하면 커버리지가 크게 준다. 되묻기가 선행 조건인
이유가 이것이다.

### 10.3 되묻기를 한 번이 아니라 이어서 (담당자 제시 방향, 미구현)

지금 되묻기는 **한 번**을 전제로 만들어져 있다. 부족한 것이 여럿이어도 한 번에 하나만
묻고, 그 답으로 계획이 서지 않으면 다시 물을 뿐 앞의 답을 이어 쌓아 좁혀 가지는 않는다.

담당자가 제시한 방향은 필요하면 **타고 들어가는 것**이다.

```text
"과목 알려줘"
   → 무엇을 알고 싶으신가요?      [개설 교과목]
   → 어느 학과인가요?             [컴퓨터공학과]
   → 몇 학년 몇 학기인가요?       [2학년 1학기]
   → 답변
```

기반은 이미 있다. `resolved` 는 항목이 쌓이는 구조이고 화면도 값을 누적해 보낸다. 실제로
`MAX_ROUNDS = 3` 상한도 이 전제로 두었다. 지금 없는 것은 다음 세 가지다.

| 필요한 것 | 지금 상태 |
|---|---|
| 앞 답을 반영해 **다음 후보를 좁히기** | 선택지 생성이 질문만 보고 만든다. 학과를 골라도 과목 후보가 그대로다 |
| 무엇이 아직 부족한지 **누적 판단** | 매 턴 계획을 처음부터 다시 세우므로 앞 턴의 부족 판단이 남지 않는다 |
| 되묻기 **횟수와 도달률 측정** | 몇 번 만에 답에 닿았는지 세지 않는다 |

첫 번째가 핵심이다. `ClarificationChoices` 가 `resolved` 를 함께 받아 이미 확정된 범위로
후보를 거르면, 두 번째 되묻기가 첫 번째 답을 실제로 이어받는다. 지금 구조에서 크지 않은
변경이지만, 측정 없이 넣으면 되묻기가 늘기만 하고 도달률이 나아졌는지 알 수 없다.
그래서 10.4 를 선행 조건으로 둔다.

### 10.4 측정 없는 개선은 넣지 않는다
