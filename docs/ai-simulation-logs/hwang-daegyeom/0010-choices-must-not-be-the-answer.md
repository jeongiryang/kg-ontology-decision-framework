## 1. 작업 목적

담당자가 화면에서 `균형교양 이수요건은?` 의 되묻기를 보고 두 가지를 지적했다.

1. 선택지 5개 중 3개가 균형교양이 아니었다(기초교양·대학영어).
2. **"이런 식이면 선택지가 의미가 있을까?"** — 선택지 라벨이 곧 답변 문장이었다.

이 로그는 그 둘의 원인과 수정을 남긴다. 0008이 "되묻기에 자격을 두었다"면 이것은
"되묻는 축을 올렸다"이다.

## 2. 요청 내용 요약

시간순이다. 뒤 요청이 앞 요청의 범위를 정했다.

1. "질문을 뭐 했는지 까먹잖아 … 어떤 질문 → 선택지를 선택해서 답변이 되었는지 표시하게"
   (→ 0008에서 반영. 이 화면 덕에 아래 문제가 보였다)
2. (화면 캡처) "이거 이런 식으로 되면 답변 가능한 게 다 나오는 거 아닌가. 이런 식이면
   선택지가 의미가 있을까? 어떻게 생각함?"
3. "지금 어디가 문제이고 어디를 고쳐야 할까? 이유하고 다 알려줘"
4. "1번 2번은 진행하고 3번은 뭔데?"
5. "3번을 진행해서 선택지가 답변인 거 고칠 수 있어? 어떤 식으로 고친다는 거임? 나는
   지금 `자료구조?` → 자료구조의 어떤 걸 묻는지 되묻기(선택지) → `자료구조 학점은?`
   → `3학점`(답변) 이런 식으로"
6. "너가 추천한 순서로 고치자"
7. (모드 뒤집힘을 보고) "왜 이런 문제가 발생했고 어떻게 고칠 수 있어?"

요청 5가 결정적이다. 담당자가 원한 축은 **"어느 사실인가"가 아니라 "그 사실의 무엇을
묻는가"** 였다. 에이전트가 앞서 제안한 축(영역별로 나누기)보다 이쪽이 맞았고, 이후 설계를
이 요청에 맞췄다.

## 3. 작업 전 상태

- 0008 종료 시점. 자연어 21문항 범위 안 17/19.
- `균형교양 이수요건은?` → 선택지 5개. 균형교양 2건 + 기초교양 2건 + 대학영어 1건.
- 규칙 선택지 라벨 = `description_ko`. 규칙 답변도 `description_ko`. **글자까지 같았다.**
- `자료구조?` → 되묻지 않고 개설 정보를 통째로 답했다.

## 4. 수행한 작업

문제를 셋으로 나눠 담당자에게 보고하고, 담당자가 순서를 정했다(1·2 먼저, 3은 설명 후 승인).

### 4.1 문제 1 — 선택지에 점수 문턱이 없었다

순위 자체는 옳았다. 균형교양 2건이 1·2위였다. 문제는 **자리 수만큼 채운 것**이다.

```text
18.467  균형교양 4개 영역에서 영역별로 각 1과목 이상 이수한다.
15.270  균형교양을 최소 12학점 이수한다.
────────  문턱 13.850 (최상위의 75%)
12.341  대학영어 이수 면제는…        ← 화면 3번
12.264  기초교양 글로벌의사소통…      ← 4번
12.264  기초교양 미래설계…           ← 5번
```

무관한 규칙이 12점이나 받는 이유는 2-gram 방식이다. `균형교양 이수요건은?` 은
`균형/형교/교양/균형교양/이수/요건/…` 으로 쪼개지고, 기초교양 규칙은 그중 `교양` 과
`이수` 두 개만 겹쳐도 점수를 받는다. 구분되는 조각(`균형` vs `기초`)이 묻힌다.

**계획기에는 이 자르기가 이미 있었다.** `_rules_related_to()` 가 `RULE_SCORE_RATIO=0.75`
로 꼬리를 잘랐고 주석에도 "꼬리까지 실으면 종전처럼 묻지 않은 요건까지 답에 섞인다"고
적혀 있었다. **넓히기를 없앨 때 계획기만 고치고 선택지 생성기를 빠뜨린 것이다.** 없앤 줄
알았던 결함이 되묻기 화면으로 자리를 옮겨 살아남아 있었다.

`fact_index.leading_candidates()` 로 공용화하고 양쪽이 쓰게 했다. `RULE_SCORE_RATIO` 는
중복이라 제거했다.

### 4.2 문제 2 — 검색 색인이 그래프를 버린다

`FactIndex.from_bundle()` 은 사실 하나를 납작한 텍스트 문서로 만든다. 쓰는 관계는
`SUPPORTED_BY`(근거 확인)와 `OF_COURSE`(과목명 끌어오기) 둘뿐이고, 다음은 버린다.

```text
TARGETS    → EducationArea       43건
APPLIES_TO → ApplicabilityScope  77건
OVERRIDES  → Rule                14건
```

지식그래프인데 되묻기와 계획이 관계를 안 보고 문자열만 본다. 그래서 `균형교양` 과
`기초교양` 의 차이를 낱말 겹침으로 추측할 수밖에 없었다.

`ClarificationChoices` 가 그래프를 직접 읽게 했다. 질문이 영역을 말하면 그 영역의 규칙만
남긴다. 영역은 두 곳에서 읽는다.

- `Rule -[:TARGETS]-> EducationArea` — 정본
- 규칙의 검증된 원문에 적힌 영역 이름 — **보완이 필요했다.** 규칙 27건 중 **12건은
  `TARGETS` 가 없다.** 화면에 나온 오답 3건 중 2건(`기초교양 글로벌의사소통`,
  `대학영어 면제`)이 여기 해당해, 관계만으로는 못 걸렀다.

영역 이름은 코드에 적지 않고 `EducationArea.name_ko` 에서 읽는다. 다만 전공 영역은 이름이
`컴퓨터공학 전공필수` 라 사용자가 `전공필수` 라고만 물으면 겹치지 않아, **공백으로 나뉜
마지막 조각도 함께 대조**한다.

### 4.3 문제 3 — 선택지 라벨이 곧 답변이었다

담당자 지적의 핵심이다.

```text
선택지:  균형교양 4개 영역에서 영역별로 각 1과목 이상 이수한다.
   ↓ 클릭
답변:    균형교양 4개 영역에서 영역별로 각 1과목 이상 이수한다.
```

규칙 답변은 `description_ko` 를 그대로 내보내고, 선택지 라벨도 같은 `description_ko` 였다.
사용자는 답을 읽고, 그것을 눌러, 같은 문장을 다시 본다. **고르는 행위가 정보를 주지 않는다.**

문제 1·2를 고쳐도 남는다. 되묻는 **축**이 한 단계 낮기 때문이다.

| 축 | 되물을 가치 | 이유 |
|---|---|---|
| 조회 종류 | 있음 | 라벨 `학사규칙`, 답이 아님 |
| 학과·학년도 | 있음 | 라벨 `컴퓨터공학과`, 답이 아님 |
| 동명 과목 | 있음 | 라벨 `자료구조(CDA0008)`, 답이 아님 |
| **어느 규칙 문장인가** | **없음** | **라벨이 곧 답** |

원칙을 하나로 정했다. **선택지 라벨은 "무엇을 물을지"이며 절대 "답"이면 안 된다.**
축이 둘로 갈렸고, 담당자가 정한 순서(B → A)로 진행했다.

#### B. 주제 축 (규칙)

라벨을 `적용 대상 · 영역 · 기준 종류` 로 조립한다. 세 조각 모두 선언된 표기이며 새로
요약하지 않는다.

| 조각 | 출처 |
|---|---|
| 적용 대상 | `ApplicabilityScope` 의 `student_type`·`college_category` + 통제어휘 표기 |
| 영역 | `EducationArea.name_ko` |
| 기준 종류 | `rule_type` 통제어휘의 `description_ko` |

```text
전:  [균형교양을 최소 12학점 이수한다.]
후:  [일반 적용 대상 · 균형교양 · 학점 요건]  →  균형교양을 최소 12학점 이수한다.
```

**라벨이 같아지는 규칙은 한 선택지로 묶는다.** 그 라벨로는 구분되지 않으므로 갈라 놔도
고를 수 없고, 묶으면 고른 뒤 둘 다 답한다. 값이 처음부터 목록(`rule_ids`)이라 그릇을
바꾸지 않아도 됐다.

#### A. 속성 축 (과목) — 담당자가 제시한 형태

```text
자료구조?
  ↳ 무엇을 알고 싶으신가요?
     [개설 학년 목록] [개설 학기] [학점] [이론 시수] [실기·실습 시수] [이수구분]
  ↳ 학점    →  자료구조는 3학점입니다.
  ↳ 이수구분 →  자료구조의 이수구분은 전공선택입니다.
```

라벨 `학점` 과 답 `3학점` 이 다르다. 고르는 행위가 질문을 실제로 좁힌다.

- 부족 코드 `COURSE_ASPECT` 와 유사 필터 `requested_fields` 를 새로 두었다. 되묻기가
  채우는 것이 필터가 아니라 요청 필드인 첫 경우다.
- 라벨은 명세의 속성 `description_ko` 에서 읽는다(`학점. 0과 빈 값은 구분` → 첫 마디만).
- **이미 속성을 말한 질문은 되묻지 않는다.** 판정 낱말도 데이터에서 얻는다. 라벨을 낱말로
  쪼개되 **여러 라벨이 함께 쓰는 낱말(`개설`, `시수`)은 뺀다.** 어느 속성을 가리키는지
  정할 수 없기 때문이다. 불용어 목록을 코드에 적지 않고 라벨끼리 대조해 얻었다.

### 4.4 곁따라 고친 것

- **묶인 선택지에서 계획이 깨졌다.** 규칙 2건을 담은 선택지를 고르면
  `FILTER_IMPLIED_MODE` 가 `rule_ids` 를 `SINGLE_RULE` 로 고정해 "규칙 하나" 계약에
  걸렸다. 조회 종류를 따로 고르지 않았을 때도 **개수가 종류를 정하도록** `_reconciled` 를
  고쳤다.
- **되묻기 게이트를 한쪽에만 달았다가 고쳤다.** `_plan_once` 에는 READY 로 나가는 경로가
  둘이다(정상 경로, `_scope_settled` 경로). 속성 되묻기를 정상 경로에만 달았더니 계획
  모델이 어느 경로로 오느냐에 따라 동작이 갈렸다. 양쪽에 같은 검사를 뒀다.

### 4.5 계획 모드가 뒤집히던 문제 (담당자 질문 7)

측정 중 `자료구조는 몇 학년 몇 학기에 개설되나?` 가 한 번은 답하고 한 번은 실패했다.
원문 payload 를 잡아 보니 **3회 모두 같은 값**이었고 재시도로 벗어나지 못했다.

```text
mode    = SINGLE_COURSE                                     ← 맞음
fields  = [recommended_grade_year, recommended_semester]    ← 틀림(권장 교양 과목 전용)
filters = {name_ko: '자료구조'}                             ← 맞음
```

모델이 **종류는 맞게, 필드는 틀리게** 골랐다. `몇 학년 몇 학기` 를 듣고 `grade_year` 대신
`recommended_*` 를 집었다. 시스템 프롬프트에 그 필드를 설명하는 줄이 있어 14B 모델이 둘을
혼동한다.

여기까지는 모델 실수인데 **우리 코드가 증폭시켰다.** `_mode_for_fields` 는 "필드가 한
family 소유면 그 모드로 고친다"는 보정이고, 주석이 전제를 밝히고 있다.

> 작은 모델은 물음의 종류를 자주 SINGLE_COURSE 로 몰아 놓고, **정작 요청 필드는 옳은**
> fact family 의 것을 고른다.

이 사례는 그 전제가 뒤집힌 경우다. 종류가 맞고 필드가 틀렸는데 보정은 필드를 믿어,
계획을 통째로 권장 과목 조회로 바꿨다.

**신호가 둘 이상 일치하면 필드 하나에 지지 않게** 했다.

| 신호 | 값 | 근거의 세기 |
|---|---|---|
| 질문이 지목한 과목 | `자료구조` | **적재 데이터와 대조해 확인** |
| 모델의 조회 종류 | `SINGLE_COURSE` | 모델 판단 |
| 요청 필드 | `recommended_*` | 모델 판단 |

앞의 둘이 "한 과목 조회"로 일치하고, 과목명은 확인된 값이라 근거가 세다. 그래서 질문이
적재된 과목을 지목했고 모델도 과목 조회라고 했으면 필드만 보고 종류를 옮기지 않는다.
과목을 지목하지 않은 질문(`1학년 1학기 권장 교과목은?`)은 종전대로 보정한다. **신호
하나로는 안 되고 둘이 일치해야 한다.**

틀린 필드는 버려도 손해가 없다. 그 모드가 줄 수 있는 것만 남기고 개설 정보로 채우는
단계가 이미 뒤에 있다.

## 6. 주요 결정과 이유

### 6.1 되돌린 판단 — 속성 정렬을 값 가짓수로 매기려던 것

값이 여러 가지인 속성이 물을 가치가 크다고 보고 정렬해 봤다. 결과가 나빴다.

```text
정렬 후: 개설 학년 목록 · 개설 학기 · 실기·실습 시수 · 학점 · 이론 시수 · 이수구분
```

`실기·실습 시수` 가 3위로 올라오고 `이수구분` 이 6위로 밀렸다. **지표가 유용함을 대신하지
못했다.** 임의로 순위를 매기느니 명세가 선언한 순서를 쓰기로 하고 되돌렸다.

### 6.2 되돌린 판단 — 속성에도 선택지 상한을 걸던 것

상한 5개를 걸었더니 6번째인 `이수구분` 이 화면에서 사라졌다. 상한은 **검색 꼬리**가 섞여
드는 것을 막으려고 둔 것인데, 속성은 스키마가 정한 **닫힌 집합**이라 꼬리가 없다.
`_CLOSED_SET_CODES` 로 이 코드만 상한에서 뺐다.

### 6.3 프롬프트를 고치지 않고 코드 가드를 넣었다

4.5의 직접 원인은 프롬프트의 `recommended_*` 설명 줄로 보인다. 그러나 0007에서 시스템
프롬프트에 한 줄 넣었다가 **관계없는 첫 질문 판단까지 규칙 조회로 끌려가** 되돌린 적이
있다. 프롬프트는 영향 범위를 예측할 수 없고 코드 가드는 조건이 명시적이다. 모델이 계속
틀려도 결과가 옳으면 그쪽이 낫다고 보고 가드를 택했다.

### 6.4 넓히기 부활이 아니다

담당자가 넓히기를 없애기로 한 결정과 겹쳐 보여 진행 전에 차이를 보고하고 승인을 받았다.

| | 종전 넓히기 | 이번 |
|---|---|---|
| 후보 선정 | 질문 낱말 ↔ 규칙 원문 **문자열 겹침** | **그래프의 영역 관계 + 점수 문턱** |
| 결과 | 묻지 않은 요건이 섞임 | 균형교양 질문 → 균형교양만 |

넓히기가 실패한 원인(문자열 겹침)이 되묻기에 그대로 남아 있었고, 이번에 그것을 제거했다.

## 8. 발견된 문제와 위험

- **규칙 27건 중 12건에 `TARGETS` 영역 관계가 없다.** 원문에서 영역 이름을 읽어 보완하고
  있으나, 원문이 영역을 말하지 않는 규칙은 영역으로 거를 수 없다. 적재 쪽에서 관계를
  채우는 것이 정공법이며, `data/verified/` 변경이라 담당자 판단이 필요하다.
- **규칙 답변은 여전히 `description_ko` 원문 그대로다.** 라벨만 분리했을 뿐 답변 형식은
  바꾸지 않았다.
- **전공 영역 이름의 마지막 조각을 쓰는 규칙은 표기 관례에 기댄다.** `컴퓨터공학 전공필수`
  → `전공필수`. 영역 이름에 공백 규칙이 달라지면 함께 봐야 한다.
- `자료구조?` 가 개설 정보를 통째로 답하던 동작이 되묻기로 바뀌었다. 0006에서 담당자가
  "3학점입니다"만 나온다고 지적해 전 필드로 넓힌 자리이며, 이번에 되돌린 셈이다.
  **담당자 승인 아래 바꿨고**, 이제는 사용자가 원하는 속성을 직접 고른다.
- 담당자 화면 실측은 아직 없다. 서버는 `127.0.0.1:8501` 에 띄워 둔 상태다.
