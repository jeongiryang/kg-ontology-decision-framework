## 1. 작업 목적

0006에서 되묻기를 **한 번** 하도록 만들었다. 그 한 번으로 좁혀지지 않는 질문은 선택지를
누르고도 답을 받지 못했다. 이번 작업의 목적은 두 가지다.

1. **답할 수 있는 조건이 갖춰질 때까지 선택지를 타고 들어가게 한다.**
2. **누를 수 있는 선택지는 답변 가능한 것만 뜨게 한다.** 골라도 답에 닿지 못하는
   막다른 선택지를 없앤다.

단, 무조건 타고 들어가지 않는다. 이미 충분하거나 가능한 답이 하나뿐이면 곧바로 답한다.

## 2. 요청 내용 요약

담당자 요청을 시간순으로 적는다. 뒤 요청이 앞 요청을 좁혔다.

1. "어제 진행하다가 미처 다 진행 못 한 거 다 진행하고, 되묻기에서 선택지를 선택해서
   계속 질문에 답이 어려우면 더 타고 들어갈 수 있게, 답을 할 수 있는 조건이 완성될
   때까지 타고타고. 선택지를 누를 수 있는 선택지는 답변 가능한 것만 뜨고."
2. "답변 남기지마" — 정이량이 PR #29에 남긴 리뷰에 답변하지 않는다.
3. "무조건 선택지를 타고들어가는 게 아니라 답변 가능할 정도로 충분한, 아니면 1개의
   답변만 가능하다면 그럴 땐 바로 답변할 수 있도록."
4. "50문장은 너의 성능을 고치는 데 사용하지 마 일단" — `eval/` 평가 질문셋을 튜닝
   기준으로 쓰지 않는다. 측정에는 별도의 21문항 임시 집합만 썼다.

요청 3이 요청 1을 좁혔다. 연쇄는 필요할 때만 하고, 이미 정해진 것은 묻지 않는다.

## 3. 작업 전 상태

0006 종료 시점의 상태다.

- 되묻기 선택지는 데이터에서 만들어졌고, 사용자가 고른 값은 같은 선택지를 다시 만들어
  대조한 뒤에만 받아들였다(무상태 검증).
- 그러나 **한 턴으로 끝났다.** 조회 종류(`selection_mode`)만 고른 상태에서 다음으로
  갈 곳이 없었다.
- 자연어 21문항 측정: 범위 안 **16/19**.

### 이번에 확인한 사실 (작업 전에는 몰랐던 것)

실제 서버로 연쇄를 흉내 내 보고서야 드러난 것들이다.

| 현상 | 실제 원인 |
|---|---|
| `과목 알려줘` → 종류·규칙을 다 골랐는데 3턴에서 빈손 | `MULTIPLE_RULES` 를 고른 뒤 규칙을 **하나** 고르면 계획 계약이 "규칙 두 개 이상"을 요구해 깨짐 |
| 다 고른 뒤에도 계획이 서지 않음 | 되묻기 payload 는 계획을 접은 껍데기라 `requested_fields` 가 비어 있음 |
| 고른 조회 종류가 뒤집힘 | `_mode_for_fields` 가 껍데기에 남은 앞 시도의 필드로 사용자의 선택을 덮어씀 |
| 과목을 골랐는데 `QUERY_CYPHER_GENERATION_FAILED` | `SINGLE_COURSE` 계획에 Rule 전용 `description_ko` 가 섞임. 기본 네 모드에는 필드 거르기 단계가 없었음 |
| 과목 목록을 골랐는데 `ANSWER_CLAIM_VALIDATION_FAILED` | `COURSE_LIST` 에 `name_ko` 가 없어 목록의 주어를 만들 수 없음 |
| `산학캡스톤디자인1은(는)` | 조사 판정이 마지막 글자가 한글 음절일 때만 동작. 숫자로 끝나는 과목명에서 두 형태가 함께 출력됨 |
| `컴퓨터공학과 자료구조는 몇 학년 몇 학기?` → `NOT_FOUND` | 계획 모델이 적재에 없는 `CS101` 을 지어냈고, 기존 가드는 "과목 필터가 **있는지**"만 보고 "그 과목이 **맞는지**"는 보지 않았음 |

## 4. 수행한 작업

### 4.1 뒤의 좁은 선택이 앞의 넓은 조회 종류를 고치게 함

`LocalQueryPlanner._reconciled()` 를 추가했다. 고른 `rule_ids` 가 하나면
`SINGLE_RULE`, 둘 이상이면 `MULTIPLE_RULES` 로 맞춘다. 조회 종류를 추측해 바꾸는 것이
아니라 **고른 개수가 이미 정해 놓은 종류로 맞추는 것**이다.

### 4.2 다 고른 뒤에는 조회할 수 있는 계획이 나오게 함

`_normalise()` 에 세 가지를 넣었다. 모두 값을 지어내지 않는 구조적 보강이다.

- 고른 모드가 줄 수 없는 필드를 떨어뜨린다(`allowed_fields_for_mode`). 확장 family 는
  이미 걸러지고 있었고 기본 네 모드에만 이 단계가 없었다.
- 그러고도 요청 필드가 비고 규칙을 골랐다면, **그 규칙이 실제로 갖고 있는 필드**를
  요청한다(`_fields_every_rule_has`). 없는 필드를 요청하면 결과 검증이 조회를 막는다.
- `COURSE_LIST` 에 `name_ko` 를 넣는다. 과목 목록은 과목명이 있어야 답이 된다.

### 4.3 사용자가 고른 조회 종류를 계획기가 뒤집지 않게 함

`_settled_mode()` 를 추가하고, 사용자가 종류를 고른 요청에서는 `_mode_for_fields()`
보정을 건너뛴다.

### 4.4 계획 모델에 사용자의 선택을 알려 줌

`planner_prompt(settled_choices=...)` 로 고른 값을 전달한다.

**한 번 되돌린 시도가 있다.** 처음에는 이 지시를 `PLANNER_SYSTEM_PROMPT` 에 상시로
넣었다. 그러자 **고른 값이 없는 첫 질문의 판단까지 규칙 조회 쪽으로 끌려갔다.**

| 질문 | 상시 지시 전 1턴 | 상시 지시 후 1턴 |
|---|---|---|
| `과목 알려줘` | `selection_mode` 3개 | `rule_ids` 5개 |
| `캡스톤 과목 알려줘` | `course_code` 2개 | `rule_ids` 5개 |
| `2026학년도 전공필수 학점 얼마야?` | `selection_mode` 2개 | `rule_ids` 5개 |

`캡스톤 과목 알려줘` 에 균형교양 규칙을 답하는 상태가 됐다. 되돌리고
`SETTLED_CHOICES_DIRECTIVE` 로 분리해, **고른 값이 있을 때만** 사용자 프롬프트에
붙인다. `user_settled_choices` 키도 비어 있으면 아예 싣지 않는다.

### 4.5 지어낸 학수번호를 막음

- 계획 컨텍스트에 `course_codes_by_name` 을 만들었다. 프롬프트에는 싣지 않는다
  (`INTERNAL_CONTEXT_KEYS`).
- `_ignores_named_course()` 가 필터 **값**까지 대조한다. 지목한 과목이 실제로 그
  학수번호를 갖지 않으면 계약 위반으로 되돌린다.
- 되먹이는 오류 문구에 지목한 과목명과 적재된 학수번호를 담는다
  (`_named_course_error`). 종전 문구("과목 필터가 없다")는 이 경우 틀린 진단이라
  모델이 같은 값을 다시 냈다.

### 4.6 질문에 과목명이 그대로 있으면 검색을 쓰지 않음

`ClarificationChoices._named_courses()` 를 추가했다. 질문에 적재된 과목명이 그대로
등장하면 검색 상위 다섯을 늘어놓지 않고 그 과목만 내놓는다. `자료구조` 는
`고급자료구조` 의 부분 문자열이므로 **가장 긴 이름만** 남긴다.

결과로 선택지가 하나가 되고, 기존 자동 채택(`_safe_to_adopt`)이 걸려 사용자는 클릭
없이 답을 받는다. 요청 3("1개의 답변만 가능하다면 바로 답변")이 여기서 성립한다.

### 4.7 숫자로 끝나는 이름의 조사

`_DIGIT_HAS_FINAL` 을 두어 읽는 소리로 받침을 정한다(0 영·1 일·3 삼·6 육·7 칠·8 팔은
받침 있음, 2 이·4 사·5 오·9 구는 없음). `산학캡스톤디자인1은(는)` → `산학캡스톤디자인1은`.

### 4.8 테스트

`tests/test_clarification_flow.py` 에 두 묶음을 더했다.

- `ChainedClarificationTests` — 좁혀짐, 막다름 없음, 이미 고른 자리는 다시 묻지 않음,
  개수에 따른 종류 보정, 조회 종류는 대신 고르지 않음, 개체 하나는 자동 채택, 상한.
- `SettledPlanTests` — 껍데기 payload 로도 조회 가능한 계획이 나오는지, 잔재 필드가
  사용자의 선택을 뒤집지 않는지, 모드가 줄 수 없는 필드가 떨어지는지, 과목 목록이
  과목명을 갖는지.

## 6. 주요 결정과 이유

### 6.1 조회 종류는 후보가 하나여도 대신 골라 주지 않는다

`_safe_to_adopt` 는 `selection_mode` 을 자동 채택하지 않는다. 후보가 하나로 좁혀졌다는
것은 그 종류로만 답할 수 있다는 뜻이 아니라 **검색이 약하게 걸렸다는 뜻일 수 있다.**
반면 개체(과목·이수요건)가 하나뿐인 것은 데이터가 정한 사실이므로 자동 채택한다.

### 6.2 계획 모델에게 주는 지시는 상시로 두지 않는다 (되돌린 판단)

4.4에 적은 대로 상시 지시가 첫 질문 판단을 망가뜨렸다. **되돌린 근거는 위 표의 실측이다.**
프롬프트 지시는 그것이 적용될 상황에서만 넣는다.

### 6.3 지어낸 값은 "있는지"가 아니라 "맞는지"로 막는다

필터가 채워졌다는 것만으로는 계획이 옳다고 볼 수 없다. 적재 데이터와 값을 대조해야
한다. 이 판단은 이번에 `course_code` 에만 적용했고 다른 식별자는 남은 작업이다.

### 6.4 `eval/` 50문항은 튜닝에 쓰지 않는다

담당자 지시(요청 4)다. 측정은 21문항 임시 집합으로만 했고 그 집합은 저장소에 남기지
않았다.

## 8. 발견된 문제와 위험

- **계획 모델이 존재하지 않는 학수번호를 만든다.** `CS101` 이 3회 시도에서 3회 모두
  나왔다. 지금은 `course_code` 에 한해 적재 데이터와 대조해 막는다. `rule_id`,
  `department_id` 등 다른 식별자에는 같은 대조가 없다.
- **선택지를 눌렀을 때의 결과를 미리 보장하지 않는다.** 막다른 선택지는
  `_mode_allows` 로 조회 종류 수준에서만 걸러진다. 고른 값으로 조회했을 때 행이 0건인
  경우까지는 확인하지 않는다.
- **첫 번째 선택지만 눌러 본 실측이다.** 두 번째 이후 선택지를 눌렀을 때의 경로는
  측정하지 않았다.
- 응답 시간이 문항당 3~30초다. 연쇄가 길어지면 그만큼 누적된다.
- 담당자의 화면 실측은 아직 없다. 서버는 `127.0.0.1:8501` 에 띄워 둔 상태다.
