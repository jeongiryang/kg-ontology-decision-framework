## 1. 작업 목적

이 문서는 실패 기록이 아니라 **설계 사실의 기록**이다. "지식그래프 탐색이 진행되는 동안
실시간으로 노드가 하나씩 켜지게 하자"는 요구는 자연스럽고 앞으로도 다시 나올 것이다.
같은 시도를 반복하지 않도록, 무엇을 시도했고 무엇이 왜 막았는지 실측과 함께 남긴다.

## 2. 요청 내용 요약

담당자 요청은 다음과 같았다.

- 처리 중 화면에서 노드를 하나씩 방문하며 간선 색이 바뀌는 것을 실시간으로 보고 싶다
- 지어낸 연출이면 안 된다. 실제 지식그래프에서 일어나는 동작과 같아야 한다
- 없는 기능이면 만들어라

## 3. 작업 전 상태

`0012` 에서 `PROFILE` 을 도입해 엔진이 실제로 밟은 단계(operator·행 수·DB 접근)를 받아
화면에 그렸다. 다만 이것은 **실행이 끝난 뒤의 재생**이다. 실행 중에 화면이 따라가지 않는다.

## 4. 수행한 작업

구현하지 않았다. 타당성만 실측으로 확인했다.

### 4.1 Neo4j 는 실행 중 진행 상황을 주지 않는다

`DynamicQueryExecutor.execute()` 는 `PROFILE` 을 붙여 한 번 실행하고
`result.consume().profile` 에서 통계를 얻는다. `consume()` 이후에만 존재하는 값이다.
드라이버가 operator 진행 상황을 실행 중에 알려 주는 경로는 없다.

### 4.2 승인 경로를 hop 으로 쪼개 실행해 봤다

29노드 질의(컴퓨터공학과 전공필수)의 승인 Cypher 는 hop 4개다.

```
1. CurriculumVersion -[FOR_DEPARTMENT]-> Department
2. CurriculumVersion -[HAS_OFFERING]->  CourseOffering
3. CourseOffering    -[OF_COURSE]->     Course
4. CourseOffering    -[SUPPORTED_BY]->  Evidence
```

hop k 까지만 포함하고 그 시점까지 적용 가능한 `WHERE` 만 붙인 prefix 질의를 만들어
`CypherValidator` 에 넣었다. 파라미터는 승인된 것을 그대로 바인딩했다.

| prefix | 결과 | 막힌 규칙 |
|---|---|---|
| hop 1 (`FOR_DEPARTMENT` 까지) | 막힘 | `CYPHER_FILTER_BINDING` — 계획 필터 `completion_type` 이 바인딩되지 않음 |
| hop 2 (`HAS_OFFERING` 까지) | 막힘 | `CYPHER_VERIFIED_FILTER_REQUIRED` — 사실·Evidence VERIFIED 리터럴이 정확히 2개여야 함 |
| hop 3 (`OF_COURSE` 까지) | 막힘 | `CYPHER_VERIFIED_FILTER_REQUIRED` |
| 우회 A. 근거 경로를 처음부터 포함, 요청 필드 없음 | 막힘 | `CYPHER_RETURN_FIELD_MISMATCH` |
| 우회 B. A + `Course` hop | 막힘 | `CYPHER_RETURN_FIELD_MISMATCH` |

통과한 prefix 가 없어 hop 별 실행 시간은 측정하지 않았다.

## 5. 변경된 파일

없음. 구현하지 않았다.

## 6. 주요 결정과 이유

### 6.1 세 규칙이 부분 질의와 구조적으로 양립하지 않는다

검증기가 요구하는 것은 다음 셋이다.

1. 계획의 모든 필터를 `WHERE` 에서 **정확히 한 번씩** 쓸 것
2. `fact -[:SUPPORTED_BY]-> Evidence` **직접 경로가 정확히 하나**이고 양쪽 모두 VERIFIED
3. `RETURN` 별칭이 계약과 **정확히 일치**할 것 (요청 필드 + 범위 필터 + 근거 8종 + `scope_identity`)

중간 hop 은 아직 필터가 닿는 노드에 도달하지 못했으므로 1 을 만족할 수 없다. 근거 경로를
처음부터 붙이면 그건 이미 마지막 hop 이고, 그때는 3 이 막는다. **모든 필드가 다 모여야
통과하는 설계라 정의상 "부분"이 존재할 수 없다.**

### 6.2 이 설계는 의도된 것이며 시각화를 위해 완화하지 않는다

"모든 필드가 다 모여야 통과" 는 근거 없는 답이 새지 않게 하려는 의도된 설계다. 답변에
쓰이는 값은 반드시 VERIFIED 사실과 VERIFIED Evidence 가 직접 연결된 행에서만 나온다.
부분 질의를 허용하려면 이 보장을 느슨하게 해야 하고, 그러면 근거 없는 답이 새는 경로가
늘어난다. **화면을 예쁘게 만들자고 이 프로젝트가 지키는 것을 깨지 않는다.**

### 6.3 행 스트리밍 대안도 접었다

`execute()` 가 이미 `for record in result:` 로 행을 하나씩 받으므로, 도착하는 대로 화면에
노드를 채우는 방식은 기술적으로 가능하다. 승인된 단일 질의를 그대로 쓰므로 안전 경계도
건드리지 않는다. 그럼에도 하지 않기로 했다.

- 질의 실행은 **33ms** 인데 전체 파이프라인은 LLM 호출 때문에 **수십 초**다. 사용자가
  진행 화면을 보는 시간의 대부분은 질의 실행 이전이고, 행이 도착하는 33ms 구간은
  눈에 띄지 않는다.
- 눈에 띄게 하려면 늘려야 하는데, 그러면 "진행 중 화면은 실측 그대로" 원칙과 충돌한다.
- 늘려도 **hop 별 후보와 탈락은 여전히 못 그린다.** 그건 실행 전에 존재하지 않는 정보다.

비용 대비 얻는 것이 없다.

### 6.4 그래서 화면은 실행 후 재생이고, 그 사실을 밝힌다

결과 화면 재생은 이미 끝난 일을 사람이 보라고 다시 그리는 것이다. 감추지 않고 화면에
적는다.

```
실측 8.9ms · 사람이 볼 수 있도록 1356배 느리게 재생 중
실측 8.9ms · 재생 완료
```

순서·행 수·DB 접근 횟수는 전부 `PROFILE` 실측이다. 늘린 것은 재생 속도뿐이고 그 배율을
화면에 적는다. 진행 중 화면은 실측 그대로 두어 두 화면의 성격을 구분한다.

## 10. 다음 작업 제안 — 팀 논의 안건

아래는 **결론이 아니라 선택지와 대가**다. 담당자 판단 밖이며 팀에서 정할 일이다.

### 안건: 화면 전용 읽기 경로를 별도 검증 규칙으로 분리할 것인가

**선택지 1 — 현행 유지 (지금 상태)**

- 부분 질의 불가 → 실시간 탐색 시각화 불가
- 화면은 실행 후 재생. 순서와 작업량은 실측이며 재생 배율을 화면에 밝힘
- 얻는 것: 근거 보장이 한 곳에서만 정의되고 예외가 없다
- 잃는 것: 진행 중 화면에서 그래프가 EXPLAIN 승인 이후에야 나타난다

**선택지 2 — 화면 전용 읽기 경로를 분리**

`RETURN` 계약과 필터 바인딩 규칙을 답변용 경로에만 적용하고, 화면 전용 조회에는
별도의 느슨한 규칙(읽기 전용·LIMIT 상한·온톨로지 라벨 검사만)을 두는 방식이다.

- 얻는 것: hop 단위 실행이 가능해져 실시간 탐색과 hop 별 후보·탈락 표시가 가능
- 잃는 것: **근거 없는 답이 새는 경로가 하나 늘어난다.** 화면 전용 경로의 결과가
  답변에 섞이지 않는다는 것을 코드로 강제해야 하고, 그 강제가 깨지면 검증되지 않은
  값이 사용자에게 노출된다
- 필요한 것: 두 경로를 타입 수준에서 분리(예: 화면 전용 결과는 `ChatResponse` 에
  닿을 수 없는 별도 타입), 그 분리를 깨는 변경을 막는 테스트

**선택지 3 — 부분 확인용 별도 질의를 계약 안에서 정의**

hop 별 prefix 대신, 각 hop 의 도달 노드 수만 세는 집계 질의를 계약에 정식으로 추가한다.

- 얻는 것: 검증 경계를 넓히지 않고도 "몇 개에서 몇 개로 좁혀졌는가" 를 실행 중에 표시
- 잃는 것: 질의 왕복이 hop 수만큼 늘어 총 실행 시간이 증가. 33ms 기준으로는 문제가
  아닐 수 있으나 측정이 필요하다
- 확인되지 않은 것: 집계 질의가 현행 `RETURN` 계약과 어떻게 공존할지. 검토하지 않았다

### 판단에 필요한 것

이 결정은 "시각화의 가치" 와 "근거 보장의 단순함" 을 맞바꾸는 문제다. 시연 목적이
근거 추적을 보여 주는 것이라면 선택지 1 이 목적에 더 부합할 수 있다. 팀에서 정한다.

## 갱신 (2026-08-29) — 실질적 제약은 Neo4j 가 아니라 LLM 호출 시간이다

이 문서 본문은 "Neo4j 가 실행 중 진행 상황을 주지 않는다" 를 제약으로 다뤘다. 그것은
사실이지만 **가장 큰 제약이 아니다.** 0014 작업에서 단계별 실측을 얻고 나서야 분포가
드러났다.

같은 요청 한 건의 단계별 소요(`COMPLETED.stage_timings_ms`, 총 10,588ms):

| 단계 | 소요 | 비중 |
|---|---|---|
| 질문 분석 (LLM) | 4,060ms | 38.3% |
| Cypher 생성 (LLM) | 6,494ms | 61.3% |
| 스키마 선택 | 1ms | |
| EXPLAIN | 6ms | |
| 그래프 실행 | 6ms | |
| 정적 검증 · 결과 검증 · 주장 구성 · 답변 생성 | 0ms | |
| **LLM 두 단계 합계** | **10,554ms** | **99.7%** |
| **나머지 7단계 합계** | **13ms** | 0.1% |

여기서 나오는 결론은 세 가지다.

1. **사용자가 진행 화면에서 보내는 시간의 거의 전부가 LLM 호출 두 번이다.** 그래프
   질의는 6ms 다. hop 단위 실시간 중계가 가능해진다 해도 사용자가 그것을 보는 시간은
   전체의 0.06% 다.
2. **5~9단계는 같은 프레임 안에서 끝난다.** 단계별로 그림이 달라지는 것을 눈으로
   확인시키려면 지연을 넣는 수밖에 없고, 그것은 "측정값만 보여 준다" 는 원칙과
   충돌한다. 0014 에서는 넣지 않았다.
3. **실시간 시각화를 다시 시도한다면 대상은 Neo4j 가 아니라 LLM 단계여야 한다.**
   토큰 스트리밍처럼 그 6.5초 안에서 무엇이 일어나는지를 보이는 쪽이, 6ms 짜리 질의를
   쪼개는 것보다 사용자가 보는 시간에 훨씬 크게 작용한다. 다만 그 경로는 모델 원문
   노출과 맞닿아 있어 별도 판단이 필요하다(현재 계약은 모델 원문을 내보내지 않는다).

10절의 선택지 1~3 을 저울질할 때 이 숫자를 먼저 본다. 선택지 2 는 근거 보장 경로를
하나 더 만드는 대가로 **전체 체감 시간의 0.06% 구간**을 얻는 것이다.

측정 조건: 2026-08-29, 로컬 Neo4j Community + 로컬 LLM, 질의
`컴퓨터공학과 전공필수 과목은?` 의 되묻기 선택 이후 요청 1건. 단일 표본이며 LLM 응답
시간은 실행마다 달라진다. 비율의 크기는 표본을 늘려도 뒤집히지 않을 것으로 보나
확인하지 않았다.
